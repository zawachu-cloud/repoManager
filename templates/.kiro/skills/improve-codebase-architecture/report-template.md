# 架構報告模板

plan 依本模板寫 `tmp/arch-<YYMMDD>.md`。用 repo 既有用語;架構名詞固定用:模組、介面、深度(深/淺)、驗證入口(seam)。句子短,能用條列就條列,不寫「更好維護」「更乾淨」這類空話,改寫具體的好處(例如「測試只要打一個介面」「定價邏輯不再散在三處」)。

## 1. 範圍與方法

- 掃了哪些目錄或模組。
- 熱點依據(`git log` 的哪些檔常改)。沒指定範圍時才需要。
- 讀了哪些 `AGENTS.md` / `docs/`。

## 2. 候選總表

| 編號 | 名稱 | 類型 | 規模 | 建議優先序 |
|------|------|------|------|-----------|
| 1 | 一句話名稱 | 淺模組 / 概念散落 / 介面洩漏 / 難測試 / 檔案過大 | 小 / 中 / 大 | 強烈建議 / 值得探索 / 先觀望 |

## 3. 候選細節

每個候選一節,標題「候選 N:名稱」。

- **現況**:牽涉哪些檔與模組(附路徑),問題在哪。
- **deletion test**:刪掉後複雜度消失還是散到呼叫端。寫出結論與依據。
- **改了之後的樣子**:呼叫端會怎麼變。只描述效果,不設計介面。
- **好處**:具體,每條一行。
- **風險**:會壞什麼、要注意什麼。
- **規模**:小 / 中 / 大,附粗估動到幾個檔。
- **決策**:留空,第 3 步追問後填入(介面形狀、驗證入口、保留與刪除的測試、zawa 的選擇)。

非必要時不畫圖。模組關係複雜時,可用 Mermaid code block 畫相依:

```mermaid
flowchart LR
  A[呼叫端] --> B[淺模組 1]
  B --> C[淺模組 2]
  C -.洩漏.-> D[外部服務]
```

## 4. 不建議動的地方

看起來可疑但其實合理的部分,每項附理由(例如「看似淺,但有兩種實作,驗證入口有存在價值」)。沒有就寫「無」。
