# 計畫檔模板

寫進 `tmp/plan-<子項目>.md`。用 zawa 看得懂的話寫,每節只寫該節要的內容。
改寫自 mattpocock/skills 的 to-spec 模板(授權見 `NOTICE.md`)。

## 1. 問題

使用者現在遇到什麼問題,從使用者的角度寫。

## 2. 解法

解法長什麼樣,從使用者的角度寫。

## 3. 行為與驗收條件

編號列出,每條都能驗證,並對應一個使用者情境。格式:

1. 當 <情境>,使用者可以 <行為>,結果是 <可觀察的結果>

範例:

1. 當報表有 3 筆資料,使用者按下匯出,會得到 3 列加 1 列標題的 CSV 檔

涵蓋正常情況、邊界與失敗情況。

## 4. 實作決定

列出已做的決定:

- 要新增或修改的模組
- 模組的介面
- 資料庫 schema 變更(一律 additive,不 drop、不破壞性 alter)
- API 契約
- 需要特別說明的互動方式

不寫檔案路徑與程式碼片段,因為很快會過期。例外:原型留下的片段比文字更精準地表達決策時(狀態機、schema、型別),可以內嵌在該決定旁,並註明來自原型,只留決策相關的部分。

## 5. 驗證入口

測試從哪裡驗證行為。每個入口一行,寫「抓得到什麼、抓不到什麼」。

- 越少越好,理想是一個。
- 優先用既有、最高層的入口。
- 需要新入口時,放在能放的最高處。

範例:

- `匯出函式的輸入輸出`:抓得到欄位與格式錯誤,抓不到檔案下載流程。

## 6. 小功能切片

依序列出。每條寫:對應哪些驗收條件、做完可以怎麼驗證。

優先垂直切:每一片都貫穿必要的層,做完能獨立驗證。不要先做完所有資料庫、再做所有 API。

1. <切片名稱>:驗收條件 1、2;驗證方式 <...>

## 7. 不做的範圍

明確列出這次不做的事。

## 8. 實作提示(可選)

可以寫檔案路徑、既有類似程式與測試的位置。計畫檔是暫存,路徑過期無妨。

## 9. 需要 zawa 決定

列出需要 zawa 決定的事,每項附選項、影響與你的建議。沒有就寫「無」。
